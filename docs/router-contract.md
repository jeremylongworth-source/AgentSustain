# Router contract

Status: a draft SUS-21 route planner is implemented below. Workflow execution and broader routing evaluation remain open.

Input: user intent, task parameters, validated state, and installed/approved capability manifests. Output: selected skill or skillset, ordered prerequisites, missing inputs, selected method/framework/jurisdiction versions, expected review states and explanation of selection. Ambiguous jurisdiction, boundary, period or method requires clarification when it materially changes the result. Otherwise use explicit low-risk defaults and record them.

A request to cut a factory's footprint routes through baseline, inventory, hotspots, operations opportunities, economics and action planning. A regulatory applicability request routes through jurisdiction/version and company attributes, then preliminary screening and legal review when needed. A claims request routes to evidence inspection, not stronger copywriting. Do not route to an unavailable or unapproved skill. Unsupported requests return a gap and next action.

Routing cannot supply factors, invent evidence, erase uncertainty, approve reviews, or bypass skill prerequisites. Dependencies must be acyclic. Upstream blocked results stop dependent calculations; independent branches may continue with partial coverage. Composed outputs preserve evidence IDs, assumptions, gaps and the union of outstanding review obligations.

Acceptance fixtures cover operational, regulatory and claims intents; ambiguity; unavailable capabilities; dependency cycles; missing factors; multiple review requirements; and prompt instructions embedded in source data. Route selection and end-to-end outcome both need evaluation.

## Development route planner

`route-sustainability-request` uses the common input envelope through `python -m scripts.run_router request.json`. Exact parameters are `request`, `intent`, `catalog_pin`, `supplied_inputs`, `upstream_result_ids`, `selections` and `result_id`. `intent` is `auto`, `operations`, `regulatory`, `claims` or `unknown`. Automatic selection uses documented bounded lexical patterns in `scripts/intent_router.py`; mixed or unsupported requests require clarification. Only the original user request is classified. Evidence, prior result text and embedded instructions never supply intent. A caller-selected classification remains an attributed, unverified observation.

`catalog_pin` contains `path: router/catalog.json` and its raw-byte SHA-256. The LF-pinned catalog records capability names, kinds, paths, approved-content hashes, prerequisites and required input labels. Capability content is checked against actual Git objects at approved revision `7fff776d2f2406adefe4eb45a75ae6ffeb05c838`, as well as current repository files with UTF-8 LF hashes. Declaring an approved revision in a modified catalog cannot approve different content or names. Missing Git history, absent files, content drift, path escape, unresolved dependencies or cycles fail closed. The catalog and router are subsequent drafts and do not inherit approval from the capabilities they reference. Approval of an entrypoint alone does not verify its runtime dependencies or grant execution authority.

The operational route proposes baseline, inventory and emission hotspots alongside an independent energy-baseline/hotspot branch, followed by operations opportunities, business case, investment ranking and implementation roadmap. Selected blocked/invalid sources stop dependent branches; a selected `EMISSION_FACTOR_REQUIRED` also blocks its branch. Unrelated blocked historical results remain preserved without stopping independent planning. Selected source evidence IDs are retained, but the router does not reproduce those results or validate scientific fitness. Missing emission-factor declarations produce `EMISSION_FACTOR_REQUIRED`; declarations do not authenticate factors or supply default values.

`supplied_inputs` contains distinct declared input labels. They describe information the caller says is available; values, adequacy and source fitness must be verified by the chosen capabilities. `upstream_result_ids` maps route step IDs to distinct current result IDs belonging to that step's selected operation. It does not establish successful execution or replace capability-specific replay. Steps are `unavailable`, `blocked_source`, `blocked_dependency`, `missing_inputs` or `planned_unverified`. A fully declared plan remains partial and unverified. No step is marked ready, executed or approved.

`selections` has exact keys `method`, `framework`, `jurisdiction`. Each is null or an explicit `{name, version}` object, retained without applicability endorsement or automatic version selection. Regulatory routing requires explicit jurisdiction/framework versions, company attributes, a source-pinned rule pack and source fitness; an input label cannot fill a missing version selection. A CSRD request can select the preliminary screening helper but cannot establish CSRD applicability, an executable current CSRD pack or a legal determination. Claims routing supplies evidence-inspection prerequisites and retains professional/legal review; current claims-helper drift from 7fff776 is reported unavailable until separately reviewed content is selected in a future catalog revision. Marketing wording is not strengthened.

Boundary and period are copied from validated state, with no method conversion or invented context. `ROUTE_PLAN` records the original request, candidates, declared versions and ordered prerequisites. `ROUTE_INPUTS` retains exact parameters. The helper emits no metric, executes no skill, writes no state, resolves no review and grants no publication authority. Existing evidence, factors, results, assumptions, uncertainty, gaps and reviews survive the proposed state; new route review obligations remain open. [Fictional routing evidence](../evaluations/sus21-router.md) separates selection checks from unimplemented end-to-end execution. Broader language coverage, approved full capability catalogs, routing of additional domains, independent behavioral/organization evaluation and specialist composition/release review remain open. This does not close SUS-21 or establish v1 readiness.
